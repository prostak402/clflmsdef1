# ADR: Видео-доставка в MVP

## Статус
Proposed

## Контекст
Для MVP нужно быстро и предсказуемо доставлять пользовательские видео в клипы без перегрузки API-сервера и без внедрения сложного медиапайплайна на старте.

## Решение (целевой путь загрузки)
Фиксируем следующий поток загрузки и публикации видео:

1. Клиент вызывает `POST /uploads` и получает параметры для direct upload в объектное хранилище.
2. Клиент загружает видео напрямую в storage (direct upload), минуя API-сервер как прокси для контента.
3. После успешной загрузки клиент вызывает `POST /uploads/:id/complete`.
4. Бэкенд валидирует факт загрузки, фиксирует метаданные и возвращает/привязывает `assetUrl`, который сохраняется в сущности Clip.

Итог: Clip хранит `assetUrl` как канонический адрес исходного медиа-объекта.

## Ограничения MVP
Для первого релиза вводим явные ограничения:

- **Один формат контейнера**: принимаем только MP4 (`video/mp4`).
- **Максимальный размер файла**: до **250 MB**.
- **Максимальная длительность**: до **120 секунд**.
- **Базовая политика thumbnail**:
  - если клиент передал постер — используем его после базовой валидации;
  - иначе используем автогенерацию одного кадра по фиксированному правилу (например, кадр на 1-й секунде);
  - без ручной обрезки, без набора превью и без интеллектуального выбора кадра.

## Политика aspect ratio, контейнеров и отображения в feed
Для клипов в MVP фиксируем **ограниченный набор стандартных контейнеров карточек** и единые правила рендера. Этот раздел — source of truth для frontend, QA и дизайна.

### 1) Стандартные контейнеры карточек в ленте
Вместо авто-подбора на лету утверждаем 3 контейнера:

1. **Landscape**: `16:9`
2. **Portrait**: `4:5`
3. **Square**: `1:1`

Любой входящий клип маппится в ближайший контейнер из этого списка. Произвольные контейнеры в рантайме не создаём.

### 2) Размеры и resize-поведение контейнеров
Общие правила для всех контейнеров:
- высота карточки ограничивается через `min-height`/`max-height`;
- внутри диапазона используется fluid-скейлинг от ширины и текущего viewport;
- пересчёт при `resize` происходит только по брейкпоинтам/контейнерным правилам, без покадровой «дрожи».

Целевые рамки:
- **Mobile**:
  - `min-height: 320px`
  - `max-height: 86vh`
- **Desktop/Web**:
  - `min-height: 360px`
  - `max-height: 860px`

Логика при resize:
1. Сначала сохраняется выбранный контейнер (`16:9` / `4:5` / `1:1`).
2. Затем пересчитывается только физический размер в пределах min/max.
3. Если доступное пространство меньше минимума — карточка центрируется, допускается внешний скролл страницы/ленты, но контейнер не деформируется в нестандартную пропорцию.

### 3) Стратегия рендера видео, если исходник «не в формате контейнера»
Для контента, который не совпадает с целевым контейнером:
- по умолчанию используем **`object-fit: contain`**;
- разрешаем поля (**letterbox/pillarbox**);
- не используем `cover` по умолчанию в feed.

Важно:
1. Сохранение полного кадра важнее заполнения контейнера.
2. Кроп (`cover`) возможен только как отдельное продуктное решение для конкретной поверхности/эксперимента и фиксируется отдельным ADR/decision note.

### 4) Ограничения по layout shift (карточки не «прыгают»)
Чтобы соседние карточки в ленте не смещались при поздней загрузке метаданных видео:

- контейнер карточки выбирается заранее (по backend-метаданным или дефолтному фолбэку) **до начала воспроизведения**;
- после первого рендера карточки контейнер не меняется в рамках текущей сессии показа;
- late metadata (длительность, bitrate, фактическое разрешение) не должно менять высоту/ширину карточки;
- верхний бюджет cumulative layout shift для feed-сессии: **CLS ≤ 0.1**, для одиночной карточки при догрузке метаданных: **визуально 0 скачков размера контейнера**.

### 5) UX-требования к контролам поверх видео/полей
Контролы должны оставаться читаемыми и доступными как на самом видео, так и на чёрных полях:

- **Расположение**:
  - верхняя панель: в safe-area сверху;
  - actions-колонка: справа, в зоне большого пальца на mobile;
  - инфоблок и primary CTA: снизу, не перекрывают progress/системные жесты.
- **Отступы**:
  - учитывать `safe-area-inset-*`;
  - минимальные внутренние отступы интерактивных зон — не менее `12px` от краёв контейнера;
  - вертикальные интервалы между кнопками actions — не менее `8px`.
- **Читаемость**:
  - обязательны градиент/подложка или контрастная обводка для текста и иконок;
  - целевой контраст текста/иконок к фону — не ниже WCAG AA (где применимо);
  - на полях (letterbox/pillarbox) контролы не теряют визуальную иерархию и не «плавают» при смене ролика.

### Правила приоритетов
1. Стабильный контейнер карточки важнее попытки «идеально заполнить» весь экран.
2. Сохранение полного кадра (`contain`) важнее агрессивного кропа (`cover`).
3. Предсказуемость UX и отсутствие layout shift важнее адаптации под «редкие» исходные пропорции.

### Единый source of truth
Эти правила считаются каноничными и обязательными для:
- frontend-реализации;
- QA-сценариев и acceptance-checks;
- дизайн-спецификаций и макетов.

Изменения политики aspect ratio вносятся только через обновление этого ADR с синхронизацией артефактов во всех трёх направлениях.

## Граница ответственности API-сервера
API-сервер **не стримит видео напрямую** и не работает как media proxy для playback.

Его роль:

- выдавать upload-сессии;
- принимать completion-сигнал;
- хранить метаданные/ссылки (`assetUrl`);
- отдавать клиентам данные для дальнейшего воспроизведения через CDN/object storage.

## Минимум для запуска
Для production-ready MVP достаточно:

- `POST /uploads` с выдачей upload intent/presigned данных;
- direct upload из клиента в storage;
- `POST /uploads/:id/complete` с серверной валидацией завершения;
- сохранение `assetUrl` в Clip;
- базовые лимиты (формат/размер/длительность);
- простая стратегия thumbnail;
- воспроизведение через CDN/storage URL.

## Что можно отложить
Вне критического пути MVP:

- **Transcoding ladder (ABR)**: множественные битрейты/разрешения и адаптивный стриминг.
- **DRM**: лицензирование, защита ключей, интеграции с DRM-провайдерами.
- **Advanced analytics**: детальные QoE-метрики, тепловые карты просмотров, глубинная атрибуция событий playback.

## Последствия
Плюсы:

- короткий путь к запуску;
- снижение нагрузки на API-контур;
- предсказуемая стоимость и операционная простота.

Минусы/риски:

- ограниченная совместимость устройств из-за одного контейнера;
- отсутствие ABR ухудшает опыт на нестабильной сети;
- ограниченная наблюдаемость качества воспроизведения на старте.
