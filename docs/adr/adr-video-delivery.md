# ADR: Видео-доставка в MVP

## Статус
Proposed

## Контекст
Для MVP нужно быстро и предсказуемо доставлять пользовательские видео в клипы без перегрузки API-сервера и без внедрения сложного медиапайплайна на старте.

## Решение (целевой путь загрузки)
Фиксируем следующий поток загрузки и публикации видео:

1. Клиент вызывает `POST /uploads` и получает параметры для direct upload в объектное хранилище.
2. Клиент загружает видео напрямую в storage (direct upload), минуя API-сервер как прокси для контента.
3. После успешной загрузки клиент вызывает `POST /uploads/:id/complete`.
4. Бэкенд валидирует факт загрузки, фиксирует метаданные и возвращает/привязывает `assetUrl`, который сохраняется в сущности Clip.

Итог: Clip хранит `assetUrl` как канонический адрес исходного медиа-объекта.

## Ограничения MVP
Для первого релиза вводим явные ограничения:

- **Один формат контейнера**: принимаем только MP4 (`video/mp4`).
- **Максимальный размер файла**: до **250 MB**.
- **Максимальная длительность**: до **120 секунд**.
- **Базовая политика thumbnail**:
  - если клиент передал постер — используем его после базовой валидации;
  - иначе используем автогенерацию одного кадра по фиксированному правилу (например, кадр на 1-й секунде);
  - без ручной обрезки, без набора превью и без интеллектуального выбора кадра.

## Политика aspect ratio и отображения
Для клипов в MVP фиксируем единый набор классов aspect ratio и правила отображения, которые являются source of truth для frontend, QA и дизайна.

### Поддерживаемые классы aspect ratio
- **Вертикальные**: около `9:16`.
- **Горизонтальные**: около `16:9`.
- **Квадрат**: около `1:1`.
- **Промежуточные**: например `4:5`, `3:4`, `1.91:1` и близкие к ним пропорции.

### Режимы рендера по платформам
Базовое правило для всех классов:
- **`contain` — режим по умолчанию**: сохраняем полный кадр, допускаем поля (letterbox/pillarbox).
- **`cover` — только по явному продуктному согласованию**: применяется лишь там, где кроп допустим и это отдельно утверждено.

Практика по устройствам:
- **Mobile**: при несовпадении пропорций приоритет у сохранения полного кадра (`contain`).
- **Desktop**: тот же базовый режим `contain`; `cover` не включается автоматически без отдельного решения.

### Правила приоритетов
1. Если контент горизонтальный, а экран mobile вертикальный — используем **letterbox** (показываем полный кадр).
2. В feed по умолчанию **никогда не обрезаем важные зоны**.
3. Любое отклонение в сторону `cover` должно быть документировано как отдельное продуктовое решение для конкретной поверхности.

### Единый source of truth
Эти правила считаются каноничными и обязательными для:
- frontend-реализации;
- QA-сценариев и acceptance-checks;
- дизайн-спецификаций и макетов.

Изменения политики aspect ratio вносятся только через обновление этого ADR с синхронизацией артефактов во всех трёх направлениях.

## Граница ответственности API-сервера
API-сервер **не стримит видео напрямую** и не работает как media proxy для playback.

Его роль:

- выдавать upload-сессии;
- принимать completion-сигнал;
- хранить метаданные/ссылки (`assetUrl`);
- отдавать клиентам данные для дальнейшего воспроизведения через CDN/object storage.

## Минимум для запуска
Для production-ready MVP достаточно:

- `POST /uploads` с выдачей upload intent/presigned данных;
- direct upload из клиента в storage;
- `POST /uploads/:id/complete` с серверной валидацией завершения;
- сохранение `assetUrl` в Clip;
- базовые лимиты (формат/размер/длительность);
- простая стратегия thumbnail;
- воспроизведение через CDN/storage URL.

## Что можно отложить
Вне критического пути MVP:

- **Transcoding ladder (ABR)**: множественные битрейты/разрешения и адаптивный стриминг.
- **DRM**: лицензирование, защита ключей, интеграции с DRM-провайдерами.
- **Advanced analytics**: детальные QoE-метрики, тепловые карты просмотров, глубинная атрибуция событий playback.

## Последствия
Плюсы:

- короткий путь к запуску;
- снижение нагрузки на API-контур;
- предсказуемая стоимость и операционная простота.

Минусы/риски:

- ограниченная совместимость устройств из-за одного контейнера;
- отсутствие ABR ухудшает опыт на нестабильной сети;
- ограниченная наблюдаемость качества воспроизведения на старте.
